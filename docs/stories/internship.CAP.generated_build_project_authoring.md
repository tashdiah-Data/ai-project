## The business outcome
An intern's project is generated by the Student Build Pipeline rather than typed story by story, rests at drafted for review, and ships only when the reviewer approves the exact plan they read.
Intended users: Dhee, internship-section staff, intern.
## The human-operable process, as it works now
This must be operable by a person before an agent touches it. If a human cannot do it by hand
against the surfaces below, the agent version has nothing to stand on.
**Workflow**
- Generate intake questions for the intern's project
- Start the build with holdForReview so it rests at drafted
- Present the plan, its gate violations and its coverage to the reviewer
- The reviewer assigns, publishing the plan under its reviewed hash
- Task materialisation and active-project pointing follow the pipeline's own order
**Inputs**
- application id
- enrollment id
- project size tier
- intake answers
- reviewed plan hash
**Outputs**
- drafted build plan
- projects, student_task_lists and student_tasks rows on publish
- gate violation list
**Exceptions that must be handled**
- Blocking gate violations must prevent publication; advisory ones are shown and may be accepted
- A plan whose hash changed since review must not publish under the reviewer's approval
- assertNotGeneratedProject prevents a second generated project colliding with an existing one
- A model or tool failure may preserve a draft but must never advance an approved stage
- PUBLICATION IS THE REVIEWER'S ACT. An agent may generate and may propose, but assignment is a human click
